# 未検証項目と追加テスト計画

## 1. 目的

現行の自動テストで確認できたのは、DB/CUIの業務関数、Webバックエンドの主要正常系、MOCK/FakeSerialの一部、TypeScript/Vite/Arduinoのビルドである。本書では、未検証項目を重要度順に整理し、次に追加すべきテストと受入条件を定める。

## 2. 優先順位

| 優先 | 意味 | 根拠 |
|---|---|---|
| P0 | 実施前に安全性・データ損失を確認 | 本番DB破壊、誤ったsession終了、誤出席登録は復旧影響が大きい |
| P1 | 実装前後で必ず回帰させる | API/runtmeの状態・排他・DB整合性に直結 |
| P2 | Web受入前に必要 | UI、polling、復旧、エラー表示に直結 |
| P3 | 実運用開始前に必要 | 実COM、Arduino、カード、長時間運用に依存 |

## 3. P0: 本番DB保護とセッション安全性

### P0-DB-001 本番DBパスの強制ガード

- 対象: CUI/DBテスト、Web fixture、将来追加される全DBテスト。
- 方法: 本番 `attendance.db`、`-wal`、`-shm` の絶対パスを検査し、一致時はテスト開始前にFAIL。
- 期待: 一時DB以外へ書込み接続しない。
- 現状: Web test fixtureと `WEB-SAFE-001`で一部実装済み。CUI側の一時DB使用はコード確認済み。
- 追加: 共通 `assert_test_db_path()` をテストヘルパーへ集約し、全fixtureから呼ぶ。

### P0-DB-002 実DB前後監視

- 対象: テストランナー。
- 方法: 実行前後のSHA-256、WAL/SHM存在・サイズ・ハッシュを読み取り比較。
- 期待: すべて一致。差分時はPASSを出さず、実行結果を要調査にする。
- 現状: 2026-10-21に外部ラッパーで実測PASS。

### P0-SES-001 close/start競合

- 対象: `web/backend/app/routers/sessions.py` と `rfid_runtime.py`。
- 再現: start APIのOPEN確認直後で同期を止め、別スレッドでcloseを完了させ、startを続行する。
- 期待: CLOSED sessionのruntime開始は409で拒否される。
- 現状: 未実装。コード上、start routeのDB確認がcontrollerの`operation_lock`外にあるため、潜在的な不具合候補。
- 修正後のテスト: `T-LOCK-01`としてHTTP同時実行またはcontrollerの原子的操作を確認する。
- 方針: 本番コードの修正は別途承認後に実施し、今回のテスト整備では修正しない。

## 6. P2: フロントエンドとWebシステム試験

### 6.1 画面受入

ブラウザを実際に起動し、次の7画面を確認する。

1. ダッシュボード
2. 出席受付
3. 学生管理
4. 授業管理
5. 履修登録
6. 出欠履歴
7. RFID設定

各画面で、初期ロード、空データ、APIエラー、再読込、他画面への遷移、戻ったときの状態を確認する。

### 6.2 polling

| ID | 操作 | 期待結果 |
|---|---|---|
| P2-FE-001 | 出席受付を開始 | 約1秒でruntime/eventを取得、結果・集計を更新 |
| P2-FE-002 | 学生管理からRFID登録開始 | `operation_id`が完了するまでpollを継続 |
| P2-FE-003 | 登録完了event | 学生一覧を再取得し、結果表示後にpoll停止 |
| P2-FE-004 | 登録失敗event | エラー表示、再試行可能、誤って成功扱いしない |
| P2-FE-005 | server_instance_id変更 | cursorを破棄しruntime/学生/session/出欠を全再取得 |
| P2-FE-006 | 遅延・逆順レスポンス | 古い応答で新しい画面状態を上書きしない |
| P2-FE-007 | ブラウザ更新 | OPEN sessionを再取得し、自動でreaderを再開しない |
| P2-FE-008 | unmount | timer、AbortController、pollを確実に解除 |

現状の `useRuntimePolling` はserver IDとcursorの処理を持つが、reset時に業務一覧を全再取得すること、eventのoperation_idを画面状態と照合することは未確認である。

### 6.3 UI状態

- IDLEでは開始を有効化、ATTENDING/REGISTERINGでは重複開始を無効化する。
- STOPPINGではcloseを無効化し、stop完了後だけclose可能にする。
- SERIAL open失敗、READY timeout、DB busy、HTTP 404/409/422/503を利用者向けに表示する。
- CUI/Web同時利用禁止、127.0.0.1限定、COM一つの注意を表示する。
- PENDING/PRESENT/ABSENTを色だけでなく文字で表示する。

## 7. P3: 実COM・Arduino・RFID実機

| ID | 試験 | 前提 | 合格条件 |
|---|---|---|---|
| P3-HW-001 | Maker UNO + RC522配線 | CUI/Web停止、指定電源・配線 | READY、初期化状態を確認 |
| P3-HW-002 | COM接続 | 115200bps、対象COM | Webが単一COMを開閉できる |
| P3-HW-003 | UID登録 | 未登録カード | Web学生一覧に正規化UIDで追加 |
| P3-HW-004 | 出席受付 | OPEN、履修済みカード | PRESENTと時刻、集計が一致 |
| P3-HW-005 | 未登録/非履修 | 該当カード2種 | UNKNOWN_CARD/NOT_ENROLLED、DB行なし |
| P3-HW-006 | 複数カード | 複数履修者 | 各人1行、同一カード再読取は時刻不変 |
| P3-HW-007 | USB抜去 | 受付中に抜去 | エラー、OPEN維持、停止/再試行可能 |
| P3-HW-008 | Arduino再起動 | 受付停止後に再起動 | 自動再開せず、明示開始で再接続 |
| P3-HW-009 | 長時間 | 30分以上の受付 | メモリ増加、event buffer、DB件数が想定内 |

## 8. 実施順序と完了条件

```text
P0 DB保護/競合
  → P1 API/DB/runtime
  → P2 ブラウザ/UI/polling
  → P3 実COM/Arduino/カード
```

実運用開始の最低条件:

- P0-DB-001/002 PASS。
- P0-SES-001でCLOSED sessionへの誤開始がないこと。
- P1 runtime異常・排他・停止がPASS。
- P2 7画面、登録完了、出席、再起動復旧がPASS。
- P3 実機のUID読取、USB障害、再接続がPASS。
- それぞれのPASSにコマンド、ログ、画面記録、または利用者確認を紐付ける。
