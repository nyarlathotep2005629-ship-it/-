# RFID出欠管理システム テスト方針

| 項目 | 内容 |
|---|---|
| 対象 | 現行 CUI、Web バックエンド、Web フロントエンド、Arduino/RC522 連携 |
| 作成日 | 2026-10-21 |
| 方針 | 実装済みの自動テスト、今回追加したテスト、未実施の手動試験を分離する |
| 重要制約 | 本番 `attendance.db` をテストで書き換えない |

## 1. 目的

この方針は、RFID出欠管理システムについて「何をテストするか」「どのコードで検証するか」「どこまで実測できたか」を追跡可能にするためのものである。テストの PASS は、実行した範囲の検証が成功したことだけを示し、実COM、Arduino、画面操作、長時間運用の成功を推論しない。

## 2. 対象と対象外

### 2.1 対象

- `pc/database.py`、`pc/schema.sql` の SQLite 業務ルールとデータ整合性。
- `pc/reader.py` の MOCK/SERIAL、UID、READY/ERR、COM 接続処理。
- `pc/main.py` の CUI と既存 DB 操作との互換性。
- `web/backend/app/` の FastAPI、APIエラー、MOCK/SERIAL runtime、イベントカーソル。
- `web/backend/tests/` の一時DB・FakeSerialテスト。
- `web/frontend/src/` の TypeScript 型整合性と Vite 本番ビルド。
- Arduino の PlatformIO ビルド、Maker UNO + RC522 の実機結合試験計画。

### 2.2 今回の自動検証対象外

- 実COMポート、実Arduino、実RFIDカード。
- ブラウザを起動した画面受入、7画面の視覚・操作確認。
- USB抜去、Arduino再起動、通信切断からの実機復旧。
- CUIとWebを同時に使用した場合の運用保証。
- 認証、LAN公開、複数利用者、SQLiteスキーマ移行。

## 3. テストレベル

| レベル | 対象 | 主な方法 | PASSの意味 |
|---|---|---|---|
| 単体 | UID正規化、DB関数、runtime状態、エラー変換 | `unittest` / `pytest` / FakeSerial | 対象関数の指定入力・状態に対する結果が一致 |
| 結合 | DB + FastAPI、runtime + `pc.reader`差替え | FastAPI `TestClient`、一時SQLite | APIと既存DB関数の接続が成立 |
| システム | FastAPI + React + build成果物 | 起動、API、ブラウザ操作 | Web業務フローが通る。今回未実施 |
| 受入 | 実COM、Arduino、カード、利用者操作 | Windows実機・手動 | 実運用条件を利用者が確認。今回未実施 |

## 4. 自動テストと手動テスト

### 自動テスト

- CUI/DB: `tests/test_database.py` の Python `unittest`。
- Web: `web/backend/tests/` の `pytest`、FastAPI `TestClient`、`tmp_path`、`monkeypatch`。
- SERIAL疑似入力: `web/backend/tests/test_rfid_runtime.py` の `FakeSerialReader`。
- フロントエンド: `pnpm.cmd typecheck` と `pnpm.cmd build`。

### 手動・実機テスト

- Webを起動して7画面、画面遷移、ボタン状態、エラー表示を確認する。
- CUIを終了した状態でCOMを開き、HELLO/READY、UID読取、停止、再接続を確認する。
- Maker UNO + RC522 で単一カード、複数カード、USB抜去、Arduino再起動を確認する。

手動・実機試験を実行していない項目は PASS にしない。過去のユーザー確認は `USER-VERIFIED` として今回の自動テスト結果から分離する。

## 6. SQLiteテストDBの管理

### 6.1 原則

1. 実運用の `attendance.db` を読み書き・削除・移動しない。
2. CUIテストは `tempfile.TemporaryDirectory()` 配下の `test.db` を使う。
3. Webテストは pytest の `tmp_path` 配下のDBを `Settings(db_path=...)` に明示する。
4. Webテストfixtureは生成されたDBパスがプロジェクトの `attendance.db` と一致した場合に停止する。
5. テスト前後に本番DBのSHA-256、`attendance.db-wal`、`attendance.db-shm` の状態を比較する。
6. 一時DBと一時ディレクトリはテスト終了時に破棄する。

### 6.2 本番DB保護の確認

2026-10-21の実行では、本番DB SHA-256を前後で比較し、次の結果となった。

```text
BEFORE = 5B813FC5F1C9A6D4EBFF3B87DA3903F054B707C8E43301B8ABED9B214BDBDAD8
AFTER  = 5B813FC5F1C9A6D4EBFF3B87DA3903F054B707C8E43301B8ABED9B214BDBDAD8
WAL/SHM state = unchanged
```

この比較は本番DBを変更せず、ファイルハッシュと存在状態だけを読み取る。

## 7. MOCKとSERIALの使い分け

| モード | 用途 | 検証できること | 検証できないこと |
|---|---|---|---|
| MOCK | DB/API/runtimeの自動テスト | 出席結果、重複、PENDING、停止、排他、イベント | COM、HELLO/READY、カード実読取 |
| FakeSerial | SERIAL workerの単体/結合テスト | UIDイベント、worker停止、登録完了、resource解放 | pySerial・実COM・電気的接続 |
| SERIAL | 実機または実COMの手動試験 | pySerial、Arduino、READY、UID、切断復旧 | MOCKだけでは代替不可 |

## 8. 実行順序

```text
DB/CUI回帰
  → Webバックエンド（全テスト、一時DB）
  → TypeScript型チェック
  → Vite本番ビルド
  → API/画面のシステム試験
  → 実COM/Arduino/カード受入試験
```

後段へ進む前に、前段の FAIL と本番DB保護状態を確認する。実機を使用するときはCUIを終了し、Web以外のCOM占有プロセスも終了する。

## 9. 判定基準

| 判定 | 定義 |
|---|---|
| PASS | 指定したテストを実行し、すべての期待結果を満たした |
| FAIL | 実行したテストの期待結果を満たさなかった、または不具合を再現した |
| SKIP | 条件不足で意図的に実行しなかった |
| NOT RUN | 今回実行していない |
| BLOCKED | 環境・権限・機器等の外部条件で実行できなかった |
| USER-VERIFIED | ユーザーの手動確認記録。自動テストPASSとは分離 |
| PARTIAL | 対象範囲の一部だけを確認した |

## 10. 不具合の記録

不具合は、少なくとも次を記録する。

- テストID、実行日時、環境、再現入力。
- 期待結果、実際の結果、ログ/スタックトレース。
- 本番DB・COM・実機への影響有無。
- Product Failure、Test Harness Failure、Environment Failure の分類。
- 修正前のFAILと修正後の回帰テスト結果。

本番コードの変更が必要な不具合は、今回のテスト整備で勝手に修正せず、問題・再現条件・修正案を結果報告書に残す。

## 11. 既知の制約

- Webは試作段階で、ワンボタン起動は未対応である。
- FastAPIの主要APIとMOCK/FakeSerialは自動検証できるが、Reactの実ブラウザ操作は未自動化である。
- 実COM、Arduino、RC522、USB切断・再接続は今回未検証である。
- Webの開始APIはDBのOPEN確認を行った後にruntime開始へ進むため、セッション終了と受付開始のプロセス間タイミング競合は、別途確認・修正が必要である。
- CUIとWebの同時利用は技術的に防止されず、運用上禁止されている。
