## 7. 検出した問題・設計との相違

### 7.1 開始と終了のタイミング競合（要修正候補）

`web/backend/app/routers/sessions.py` の出席開始APIは、`database_service.get_open_session()` を呼んだ後に `controller.start_attendance()` を呼ぶ。`close_session()` の `operation_lock` と同じ範囲でOPEN確認から開始までを直列化していないため、次の順序が理論上成立する。

```text
start API: OPEN確認
close API: operation_lock取得 → close → 解放
start API: controller.start_attendance → CLOSED sessionをruntime開始
```

今回の本番コードは変更していない。修正案は、開始APIのOPEN確認とruntime開始を同じcontroller操作メソッド内の `operation_lock` で再確認することである。受入条件は「CLOSED sessionをruntime開始しない」である。

### 7.2 フロントエンドのreset時全状態再取得は未確認

`useRuntimePolling` は `server_instance_id` 不一致または `reset_required` を検知してcursorを0へ戻すが、学生一覧・OPEN session・出欠一覧・集計を同時に全再取得する処理は今回のブラウザ試験で確認していない。設計書が要求する復旧動作との差を、FE-POLL-002として追加確認する。

### 7.3 完了eventとoperation_idの画面側照合は未確認

runtimeはoperation_idをeventへ付与するが、`App.tsx` の登録完了処理はeventの種類を見て `registrationOperationId` を解除する。異なるoperation_idの古いeventを画面が誤採用しないことは未検証である。

### 7.4 API契約の確認事項

設計書では `/health` の詳細情報を想定しているが、現行実装のhealth responseは `status` と `service` のみである。実装または設計書のどちらを正とするかを、Web API契約確定時に決める必要がある。

## 8. 環境上の実行記録

Web `TestClient` はサンドボックス内ではWindows asyncioの自己パイプ初期化で開始前に停止した。これはテストケースのFAILではなく `Test Harness / Environment Failure` と分類した。その後、同じテスト、同じ一時DB方針、本番DBハッシュ監視付きで許可されたローカル実行環境へ切り替え、8件PASSを確認した。

PlatformIOも最初はグローバル `platforms.lock` の権限で停止したが、実機uploadを行わず、コンパイルだけを権限付きで再実行してPASSを確認した。
