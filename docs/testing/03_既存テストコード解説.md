# 既存テストコード解説

## 1. 読み方

この文書はテストコード全文を転載せず、各テストがどのソース処理を呼び、何を保証するかを説明する。対象は次の3ファイルである。

| ファイル | フレームワーク | 件数 |
|---|---|---:|
| `tests/test_database.py` | Python `unittest` | 19 |
| `web/backend/tests/test_api_flow.py` | `pytest` + FastAPI `TestClient` | 2 |
| `web/backend/tests/test_rfid_runtime.py` | `pytest` + FakeSerial/monkeypatch | 5 |
| `web/backend/tests/test_database_safety.py` | `pytest` + 一時DB | 1 |
| 合計 |  | **27** |

2026-10-21の実行では CUI 19件、Web 8件がいずれもPASSした。Webテストはルート `.venv` ではなく `web/backend/.venv` を使用する。

## 2. テストの仕組み

### 2.1 `unittest`

`DatabaseTestCase` は `setUp()` で `tempfile.TemporaryDirectory()` を作り、その中の `test.db` を `open_database()` に渡す。各テストは独立した空DBから開始し、`tearDown()` で接続を閉じて一時ディレクトリを破棄する。`self.assertEqual`、`self.assertRaises`、`self.assertRaisesRegex` で期待結果を検証する。

### 2.2 `pytest` fixture

`web/backend/tests/conftest.py` の `client` fixture は pytest の `tmp_path` に `test.db` を作成し、`create_app(Settings(db_path=...))` へ明示的に渡す。Web app はその設定を依存性上書きで各routerへ渡す。fixtureには、テストDBがプロジェクトの本番 `attendance.db` と一致した場合にFAILするガードがある。

Windowsのサンドボックス内でStarlette `TestClient`の自己パイプ初期化が停止したため、テストプロセスだけ `WindowsSelectorEventLoopPolicy` を設定している。FastAPI本体の実行設定は変更していない。

### 2.3 `TestClient`

FastAPIへHTTP相当のGET/POST/DELETEを送り、ステータスコードとJSONを検証する。テスト対象は本番サーバーやブラウザではなく、指定された一時DBを使うアプリインスタンスである。

### 2.4 FakeSerialとmonkeypatch

`FakeSerialReader` は `SerialReader` と同じ `open()`、`read_event()`、`close()` を持つ小さなテスト用代替で、UIDイベントを1件返す。`monkeypatch.setattr(rfid_runtime, "SerialReader", FakeSerialReader)` により、実COMを開かずにworkerのUID処理・DB保存・停止を検証する。実際のHELLO/READY、pySerial、電気的なカード読取は検証しない。

## 4. Web APIテスト 2件

### WEB-API-001 `test_api_flow_uses_temp_database_and_mock_runtime`

- 対象: `web/backend/app/routers/*.py`、`database_service.py`、`rfid_runtime.py`。
- 前提: `client` fixtureが一時DBへFastAPI appを生成する。
- 入力: 学生「テスト学生」、UID `ABABABAB`（scanでは小文字も使用）、授業「テスト授業」、履修、session。
- 処理: 学生/授業/履修をPOST → session開始 → MOCK runtime開始 → scan → duplicate scan → stop → close → report/events取得。
- 検証: 201/202/200、SUCCESS、ALREADY_REGISTERED、IDLE、CLOSED後のPRESENT、ATTENDANCE_RESULT event。
- 保証: 主要な正常系が一時DBとruntimeをつないで動くこと。
- 非保証: SERIAL、HTTP同時競合、画面操作、実ポート、異常系全般。

### WEB-API-002 `test_api_validation_does_not_expose_database_details`

- 対象: `schemas.py`、`errors.py`、学生POST API。
- 入力: 空氏名/不正UID、不正UID。
- 検証: HTTP 422、`VALIDATION_ERROR`、`code/message/request_id/retryable`以外を返さない。
- 保証: Pydantic/業務入力エラーの安全なHTTP形式。
- 非保証: DB重複、404、503、実際のSQL情報漏えい全経路。

## 5. Web runtimeテスト 5件

### WEB-RT-001 `test_serial_worker_fake_reader_and_stop`

`FakeSerialReader`が `EVENT_UID` を1件返し、SERIAL workerが `database.register_attendance` を呼ぶ。event取得を最大1秒待ってからstopし、一時DBのreportがPRESENTであることを確認する。FakeSerialのopen/read/close経路は通るが、実 `SerialReader` のHELLO/READYやpySerial例外は保証しない。

### WEB-RT-002 `test_mock_runtime_rejects_second_start_and_supports_cursor_reset`

MOCK runtimeを開始した状態で2回目の開始を実行し、例外codeが`RFID_BUSY`であることを確認する。event buffer size=2でイベントを発生させ、古いcursorを読むと`reset_required=True`になることを検証する。イベント内容のUI反映は保証しない。

### WEB-RT-003 `test_registration_worker_emits_completion_and_records_operation`

FakeSerialでRFID登録を開始し、開始時の`operation_id`と`REGISTRATION_COMPLETED` eventのIDが一致するまで待つ。runtimeがIDLE、`last_completed_operation_id`、terminal kind、学生名の保存を確認する。ブラウザがこのeventを受け取ることは保証しない。

### WEB-RT-004 `test_close_is_rejected_while_mock_runtime_is_active`

MOCK出席受付中のcloseが`RFID_RUNTIME_ACTIVE`になること、stop後にはcloseできることを確認する。controller内の安全性は検証するが、HTTP start routeのOPEN確認とcloseの同時実行タイミングは検証しない。

### WEB-RT-005 `test_event_cursor_rejects_previous_server_instance`

過去の固定文字列server IDでeventを取得し、`reset_required=True`と現サーバーIDを確認する。API/controllerの判定は保証するが、Reactが全状態再取得まで行うことは未検証である。

## 6. 本番DB保護テスト 1件

### WEB-SAFE-001 `test_web_test_database_path_is_not_production_database`

`tmp_path/safety.db`とプロジェクトの`attendance.db`が異なることを確認し、その一時DBへ学生POSTを実行する。実行前後に本番DBのWAL/SHM存在状態を比較する。Web test fixtureのパスガードと合わせ、テスト用DB指定の誤りを検知する。これは本番DBへの全アクセスをOSレベルで禁止するものではなく、テストコードの接続先誤りを検出する防御である。

## 7. 現在のテストコードで検証できない範囲

- `pc.reader.SerialReader`本体のHELLO/READY、行長、ASCII、pySerial例外。
- COMポート列挙、実ポート占有、USB切断、Arduino自動リセット。
- FastAPI全APIの404/409/503網羅、DB busy、SQLite競合。
- runtime開始APIのDB OPEN確認とclose APIの間のTOCTOU。
- React `useRuntimePolling`の約1秒周期、AbortController、server ID変更後の全再取得。
- 7画面のブラウザ遷移、ボタン無効化、表示、アクセシビリティ。
- TypeScript/Viteは型とビルドだけであり、ランタイムの画面品質。
- Maker UNO、RC522、複数カード、長時間運用、通信障害復旧。
